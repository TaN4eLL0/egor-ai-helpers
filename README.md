# egor-ai-helpers

Личные правила и инструменты для Claude Code. Клонируется на машину, `./install.sh`
вклеивает правила в `~/.claude/CLAUDE.md`, и они действуют во всех сессиях и
проектах.

## Установка

```bash
git clone <repo-url> ~/egor-ai-helpers && cd ~/egor-ai-helpers && ./install.sh
```

Правила подхватываются в **новой** сессии — текущая уже загрузила старый контекст.

## Почему правила не устаревают

Блок в `~/.claude/CLAUDE.md` — это копия `claude/rules/`, поэтому правка файла
правил сама по себе до сессий не доходит. Чтобы копия не отставала, `install.sh`
ставит две страховки:

- **git hooks.** `core.hooksPath` указывает на `githooks/`, и после `commit`,
  `pull` (`post-merge`), `checkout` и `rebase` (`post-rewrite`) installer
  перезапускается сам. Любое изменение правил через git сразу попадает в
  `~/.claude/CLAUDE.md`, и следующая сессия видит его без ручных шагов.
- **SessionStart hook.** `egor-ai-rules-sync.sh` в начале каждой сессии
  сравнивает блок с `claude/rules/` через `install.sh --check`. Если правила
  поменяли без коммита и блок отстал, hook пересобирает его и выводит свежие
  правила прямо в контекст этой сессии, поэтому устаревшая копия не действует
  даже один раз.

## Как это работает

`install.sh` склеивает все файлы `claude/rules/*.md` в порядке имён и вставляет
результат в `~/.claude/CLAUDE.md` между маркерами:

```
<!-- egor-ai:start -->
...
<!-- egor-ai:end -->
```

Всё вне маркеров не трогается — файл можно править руками, и рядом могут жить
managed-блоки других installer'ов (например `mobile-ai-helpers`). Повторный
запуск заменяет блок, а не дублирует.

## Структура

| Путь | Что |
|---|---|
| `claude/rules/*.md` | Правила, попадающие в `~/.claude/CLAUDE.md`. Нумерация задаёт порядок |
| `claude/agents/` | Subagent-определения → `~/.claude/agents/` |
| `claude/commands/` | Slash-команды → `~/.claude/commands/` |
| `claude/hooks/` | Хуки → `~/.claude/hooks/`; `egor-ai-rules-sync.sh` installer сам регистрирует как SessionStart |
| `githooks/` | git hooks репозитория, перезапускают installer после commit / pull / checkout |
| `tools/` | CLI-инструменты |

Пустые директории — задел под расширение, installer их молча пропускает.

Нумерация правил задаёт не только порядок склейки, но и ветвление по ситуации:

| Номер | Когда действует |
|---|---|
| `10-*` | Всегда. Основа общения: язык, длина, понятность, достоверность, отчёты |
| `20-*` | При разборе краша или бага — порог уверенности перед правкой |
| `30-*` | При написании любого кода — стиль проекта, расширяемость, читаемость, опора |

Все правила лежат в одном managed-блоке и поэтому загружены всегда, а не по
триггеру. Так надёжнее: правило вида «не применяй фикс без 93% уверенности»
бесполезно, если оно может не подгрузиться.

## Команды

```bash
./install.sh
```

```bash
./install.sh --check
```

```bash
./install.sh --dry-run
```

```bash
./install.sh --uninstall
```

`--dry-run` печатает блок, который будет записан, и ничего не меняет.
`--uninstall` убирает блок из `CLAUDE.md` и удаляет установленный payload.

## Как добавить правило

1. Создай `claude/rules/NN-name.md` — `NN` определяет порядок склейки.
2. Начни файл с заголовка `## Название` (в `CLAUDE.md` уровень `#` уже занят).
3. `./install.sh`
4. Открой новую сессию и проверь.

Плейсхолдер `{{REPO_ROOT}}` в тексте правила подставляется на абсолютный путь
checkout'а — удобно для правил, ссылающихся на скрипты этой репы.

## Правила пишутся наблюдаемо

Модель не исполняет прилагательные. `«будь краток»` не работает,
`«ответ по умолчанию 1–3 строки»` работает. На каждое неочевидное правило —
пример «было / стало».
